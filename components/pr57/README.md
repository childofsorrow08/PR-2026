1) Чому у цій моделі dev задається як default branch, а master використовується лише для релізів? Які переваги й ризики такого підходу?

- dev використовується для поточної розробки, а master для перевірених релізів. Так їх зручно розділяти, але потрібно стежити, щоб гілки не розходилися й неперевірений код не потрапляв у реліз.

2) У яких випадках варто відгалужувати release/*гілку? Що саме робиться у ній до моменту релізу?

- Коли починається підготовка конкретного релізу. У ній виправляють помилки, перевіряють програму та уточнюють версію, поки в dev може тривати розробка.

3) Чим відрізняється тег від гілки? Наведіть приклади сценаріїв використання кожного.

- Гілка рухається з новими комітами, а тег зазвичай позначає конкретний коміт. dev використовують для розробки, а v1.0 для позначення випуску.

4) Поясніть правила семантичного версіонування: коли збільшується patch/minor/major?

- patch для сумісних виправлень, minor для нових сумісних можливостей, major для несумісних змін публічного API.

5) Як переконатися, що dev містить усі зміни з release/1.1 перед закриттям релізу? Які gitкоманди допоможуть це перевірити?

- Порівняти історію та переконатися, що релізна гілка входить в історію dev. Для цього підходять `git log dev..release/1.1` та `git merge-base --is-ancestor release/1.1 dev`; git diff допомагає переглянути відмінності файлів.
