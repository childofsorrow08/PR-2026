1) Які групи помилок можуть виникнути під час виклику сервера та чим вони відрізняються за способом прояву в коді клієнта?

- Можуть бути мережеві помилки, помилки HTTP та помилки читання відповіді. Мережева помилка дає виняток без відповіді сервера, HTTP-помилка має статус, а неправильний JSON може дати помилку десеріалізації.

2) Чому не можна однаково реагувати на недоступність сервера, помилку валідації та код 500?

- При недоступності сервера варто запропонувати повторити запит, при валідації показати помилки полів, а при 500 повідомити про збій на сервері.

3) Чому перехоплювати слід лише ті винятки, для яких відома реакція? Що станеться з рештою винятків?

- Щоб не приховувати невідомі помилки. Решта передається вище по стеку до іншого обробника.

4) Яку проблему вирішує виокремлення PostServiceClient порівняно зі створенням HttpClient у кожній формі?

- Уся робота з API знаходиться в одному місці, тому форми не повторюють адреси, запити та обробку відповідей.

5) Чим відрізняється поведінка GetFromJsonAsync від GetAsync у разі неуспішного статус-коду?

- GetFromJsonAsync при неуспішному статусі кидає HttpRequestException, а GetAsync повертає відповідь, статус якої потрібно перевірити самому.

6) Чому для помилок валідації створено власний виняток PostingValidationException, а для решти неуспішних кодів достатньо HttpRequestException?

- Власний виняток дозволяє передати помилки конкретних полів і показати їх у формі.

7) Чому порожній catch або catch (Exception) без повторного генерування винятку в формі небезпечні?

- Вони приховують причину збою, після чого форма може продовжити роботу з неправильним станом.

8) Що відбувається з програмою після виклику глобального обробника UnhandledException і навіщо він тоді потрібен?

- При необробленому винятку процес зазвичай завершується. UnhandledException потрібен для останнього повідомлення та запису помилки, а не для відновлення роботи.
